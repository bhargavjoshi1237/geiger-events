# Complete event operations workflow

Date: 2 October 2026. Execution authorized by the user's request to implement all remaining workflow items with parallel agents.

## Outcome and scope

Extend the existing A1 workspace into an operational back office: people, physical resources, scheduled activities, responsibilities, programme releases and placement acknowledgements, restricted external access, attendance, evaluation cycles, tasks, reliable notification queues, reports and imports. Conference, workshop and competition use identical services. Keep existing custom records and optional per-event enablement. Advanced arbitrary formulas, offline support and full pre-acceptance academic peer review are separate products, outside the remaining items identified in the status assessment.

## Shared contracts (binding for all implementers)

Native module keys are `ops-people`, `ops-resources`, `ops-activities`. Compiled definitions have native sourceKind, version 1, capabilities records/forms and immutable core identity. The controller adds these to the registry; existing reference packs remain compatible. An explicit `enableWorkflow` staff action adds missing native modules to a clean published workspace using the existing save/publish services. Core native writes use the workflow service; generic record writes to these keys are rejected. Subtype rows reference the authoritative ops_entities composite identity. Workspace/module disabled state blocks ordinary access, preserving history.

Staff GET/POST `/api/events/{eventId}/operations/workflow` return the private snapshot or execute a command. Staff GET `/api/events/{eventId}/operations/export?kind=programme|attendance|evaluations|people` exports only authorized data as CSV with formula-injection protection. GET/POST `/api/portal/operations/{eventId}` read the restricted participant view or run an allowed command using verified existing portal sessions. POST `/api/portal/operations/invitations/accept` binds an invitation token to the signed-in portal member; possession of matching email alone does not confer identity. Staff POST `workflow` action invite creates a single-use capability and returns its token once. No ticket or organization membership is required for a portal identity that accepted an invitation.

Workflow GET snapshot DTO:

```
{ revision, enabled, people: Person[], resources: Resource[], activities: Activity[],
  assignments: Assignment[], cycles: Cycle[], evaluations: Evaluation[], attendance: Attendance[],
  releases: Release[], acknowledgements: Acknowledgement[], tasks: Task[], outbox: Notice[],
  invitations: Invitation[], identityLinks: IdentityLink[] }
```

All collection rows have `id`, every DTO uses camelCase, dates are UTC ISO strings, no secret token hashes or server credentials are projected. Lists are bounded to 500 rows per collection and signal `truncated` if the limit is reached; large imports are batched at 100 entries per command. Programme and report consumers must fail visibly on incomplete snapshots. Workflow has an independent event-scoped numeric `revision`, initially 0. Every mutating workflow command requires `{action, expectedRevision, commandId, ...payload}`. Successful mutation returns `{revision, result}`. Service input is strict, only allowlisted keys. Both database and service enforce tenant/event relationships. Database takes event lock, checks revision/replay, validates current assignment/module/access, changes rows, writes audit/receipt and advances revision atomically. A command ID exact replay returns the original response; changed request returns 409. Idempotency lookup occurs before expected-revision comparison. Database errors use existing mappings: 40001 stale, 22023 invalid, 23503 scope, 23505 duplicate. Known conflict details receive OperationsError codes via service/preflight and a dedicated P7002 schedule conflict -> 409 mapping.

Store RPC contracts:

```
ops_workflow_snapshot(p_project_id uuid,p_event_id uuid) returns jsonb
ops_workflow_command(p_project_id uuid,p_event_id uuid,p_actor_id uuid,p_command jsonb) returns jsonb
// p_command = {action, expectedRevision, commandId, requestHash, principalKind:'staff'|'portal', ...payload}
ops_workflow_claim_notices(p_limit integer,p_lease_id uuid) returns jsonb
ops_workflow_finish_notice(p_notice_id uuid,p_lease_id uuid,p_status text,p_provider_id text,p_error text) returns void
```

Workflow store methods: `snapshot(context)`, `mutate(context,command)`, `claimNotices(limit,leaseId)`, `finishNotice(noticeId,leaseId,status,providerId,error)`. Services may inject this boundary in Node tests. Database snapshot uses camelCase DTOs. Portal projection always happens server-side, and database mutations recheck current grants to prevent revocation races.

Entities and commands:

- Person `{id,name,email,contactId:null|uuid,roles:string[],revision}`; `savePerson` payload `{id?:uuid,name,email,contactId?:uuid,roles?:string[]}`. Roles allowed presenter/evaluator/staff/volunteer/participant. Optional contact must exist in same project; enforce active event/contact uniqueness. Names 1–200, email valid or empty, role count <=5. Multiple identity links allowed only through explicit acceptance/verified staff linking.
- Resource `{id,name,kind,capacity,location,availableFrom,availableUntil,revision}`; `saveResource` payload `{id?,name,kind:'room'|'equipment',capacity:int>=1,location?:string,availableFrom?:ISO|null,availableUntil?:ISO|null}`. Availability must be paired, increasing interval.
- Activity `{id,title,kind,resourceId,parentId,startsAt,endsAt,timezone,capacity,revision}`; `saveActivity` payload `{id?,title,kind:string,resourceId?:uuid|null,parentId?:uuid|null,startsAt?:ISO|null,endsAt?:ISO|null,timezone:IANA,capacity?:int|null}`. Start/end paired and increasing. Unscheduled activity allowed. Scheduled child fits parent and may inherit parent's room; parent cannot be changed to violate children. Independent room reservations cannot overlap. Capacity cannot exceed resource capacity. All timestamps include offsets; rendering uses activity timezone. No entity links hidden only in JSON.
- Assignment `{id,activityId,personId,role,cycleId,status,dueAt}`; `saveAssignment` payload `{id?,activityId,personId,role:'presenter'|'evaluator'|'staff'|'volunteer'|'participant',cycleId?:uuid|null,dueAt?:ISO|null,status?:'active'|'revoked'}`. Scope validated; active activity/person/role/cycle tuple unique; scheduled person cannot have conflicting independent commitments. Evaluation assignment requires open/draft same-event cycle. Revocation takes effect next request and at transaction boundary. Resource/person conflicts are caught on allocation, rescheduling and publication.
- Release `{id,version,createdAt,items: ActivityPlacement[]}`; `publishProgramme` payload `{}` creates immutable snapshot of scheduled activities/active assignments, validates conflicts, queues one placement notice per recipient and version. Republishing supersedes queued placement notices. `acknowledgePlacement` payload `{releaseId,activityId}` requires current release and own active presenter/participant assignment. Acknowledgements store exact released revision.
- Invitation `{id,personId,email,expiresAt,acceptedAt,revokedAt}`; `invite` payload `{personId,expiresInDays?:1..14}`, `revokeInvitation` `{invitationId}`. Service generates token, stores SHA256 only; raw token returned once; latest token cannot be recovered. `acceptInvitation` is server-only portal action `{tokenHash}` plus verified portal principal, checked expected email, no conflicting existing identity link, expiry/revocation/single-use under lock. Store principal includes verified `principalEmail` only on that action. IdentityLink `{id,personId,kind,principalId}` unique event/kind/principal. Staff link action `linkStaff` `{personId,userId}` checks actual project membership, never client-supplied membership claims.
- Cycle `{id,title,rubric:[{id,label,min,max,weight}],state:'draft'|'open'|'closed'|'released',dueAt,revision}`; `saveCycle` payload `{id?,title,rubric,state?,dueAt?}`; stable rubric IDs, finite min/max/positive weight, 1..20 criteria. Rubric immutable after first submitted result. Changing schema requires new cycle. `releaseResults` `{cycleId}` closes/releases results for that cycle. Manager-only `reopenEvaluation` `{evaluationId,reason}` preserves submitted history and resets draft; nonblank reason <=2000.
- Evaluation `{id,assignmentId,cycleId,personId,activityId,status:'draft'|'submitted',scores:object,notes,submittedAt,revision}`; `saveEvaluation` `{assignmentId,scores,notes?:string,submit?:boolean}` validates rubric ranges; draft may be partial, submission complete. Managers can inspect; portal evaluator reads/writes only own live assignment, only open cycle. Submitted revisions immutable. Submission recorded transactionally. Aggregation computes weighted normalized 0–100 per evaluator, average across submitted evaluations; no scores absent is distinct from zero. Presenter sees only released aggregate and approved shared feedback (private evaluator notes never projected to presenters).
- Attendance `{id,activityId,personId,purpose:'delivery'|'participation',status:'present'|'absent'|'excused',notes,recordedAt,revision}`; `markAttendance` `{activityId,personId,purpose,status,notes?:string}`. Manager or live assigned staff/evaluator with explicit staff role on activity; separate from ticket check-in. Append immutable correction row per change. Absent delivery creates a follow-up Task atomically (one open task per activity/person).
- Task `{id,title,personId,activityId,dueAt,status:'open'|'complete',revision}`; `saveTask` `{id?,title,personId?:uuid|null,activityId?:uuid|null,dueAt?:ISO|null,status?}`. Portal sees only own tasks and can `completeTask` `{taskId}`.
- `importPeople` `{items:PersonInput[]}` and `importActivities` `{items:ActivityInput[]}` up to 100, atomic with duplicate/cross-event validation; controller/service may loop SQL internal helper without generating per-item receipts. Import accepted legacy conference items by server-loaded IDs only; CSV/JSON import is supplied through UI with explicit format. Existing conference legacy data not dual-written.
- `retryNotice` `{noticeId}` only failed/uncertain notices; retries visible to manager. `queueReminders` `{}` queues deduplicated notices for overdue open evaluator assignments. Durable recipes are programme-published -> notices; evaluations-due -> reminders; absent-presenter -> task. No arbitrary execution or SQL from config.

Notices `{id,kind,personId,releaseId,status:'queued'|'sending'|'accepted'|'failed'|'uncertain'|'superseded',attempts,nextAttemptAt,lastError,providerId,payload}`. Claims take bounded SKIP LOCKED leases, only due active recipients/modules, and discard superseded placements/revoked access. Finish validates exact lease, expires and retries crashed sends as uncertain (no silent duplicate). Worker uses existing Geiger email client with idempotency key if provider contract supports it; cannot infer delivered from HTTP 200. Missing configuration yields visible failure. Bounded Node CLI and secret-protected internal HTTP route for scheduler; tests use local fake provider, never send real notices. Manual staff retry also supported. In-portal notices are a fallback.

## Permission and release requirements

Reuse `events.operations.view/configure/record_create/record_update/record_archive` for trusted staff; configure permission for programme publication, invitations, identity binding, cycle/results management; record action permissions for ordinary mutations, view for snapshot, archive/history for exports of sensitive evaluation details. Portal session is never staff. Current identity, assignments and revocation constrain portal reads/writes. Private tables revoke all anon/authenticated access and functions public EXECUTE; RLS enabled; schema-qualified routines and fixed search_path. Suite role-definition/grant policies must be checked in an isolated pilot; implement targeted protections if baseline suite permits privilege escalation.

Staff interface is an additional Workflow tab in the existing workspace, with people/resources/activities/schedule/assignments/programme/evaluation/attendance/tasks/notices/import/export controls, explicit enablement and clear errors. Portal has a dedicated event operations page with login/accept invitation/current placements/acknowledgements/assigned evaluations/staff attendance/tasks. Keep all existing routes/public payloads unchanged. UI retains unsaved drafts on conflict, preserves UUID command IDs on uncertain retries, aborts stale event loads, supports keyboard and narrow viewport, and represents empty/failed/forbidden/unconfigured states clearly.
